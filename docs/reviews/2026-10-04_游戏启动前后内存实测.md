# 游戏启动前后内存实测（2026-10-04）

已完成用户要求的启动前、启动中、进入世界后三阶段采样。进入世界后，tModLoader 主程序与 Steam 辅助进程的内存 footprint 合计稳定约 **2.23 GiB**；系统在启动前已经有内存压力。此次短时采样没有显示游戏占用持续增长或大量新增交换写出，不能据此确认内存是卡顿的唯一原因。

## 条件与口径

- 16 GiB Mac，macOS 26.5.2；时间均为用户时区 `America/Chicago`。
- 用户正常启动游戏，没有启用本项目暂停工具；Chrome、Codex、VS Code / Claude、Steam 在各阶段均保持运行，采样未发现这些应用的停止状态。
- 用户在 15:46 启动；客户端日志 15:47:32 记录进入世界，用户随后确认。世界尺寸 6400×1800。
- 只读采样 `top`、`vm_stat`、`sysctl`、`ps`，没有停止/退出应用、清理内存、修改游戏配置或存档。采样程序本身有少量开销。
- `top MEM` 是进程 physical footprint；本报告对游戏主程序和辅助进程合计。它与实际驻留 RAM、日志的 RAM 统计并非相同口径。应用组统计含共享/压缩等影响，不能累加得到系统总 RAM。
- 数字统一按 GiB（1024³ 字节）；聊天中的“GB”是约数。系统已用内存取 `top PhysMem` 的粗粒度显示；压缩内存已包含在其中，不另外相加。磁盘交换空间单列。

内核级别 2 在 [Apple XNU 文档](https://github.com/apple-oss-distributions/xnu/blob/main/doc/vm/memorystatus_notify.md)中为 Urgent（与 Warning 同类），不是正常级别。不要把它直接等同于活动监视器某个截图中的颜色；[Apple 的活动监视器说明](https://support.apple.com/zh-cn/guide/activity-monitor/actmntr1004/mac)指出，压力还与可用内存、交换率、联动内存及文件缓存有关。

## 能得出的结论与未测项

1. 游戏启动前后台就已占用大量内存；进入世界后游戏新增约 2.23 GiB footprint，系统压缩器占用相对基准中位数增加约 0.8–0.9 GiB。这支持“游戏使既有内存压力更重”的判断，但不能把系统变化全部归因于游戏，后台应用仍在正常活动。
2. 进入世界后的这 32 秒内，游戏 footprint 没有连续上涨；没有证据据此认定当前有持续内存泄漏。短样本同样不能排除长时泄漏。
3. 本次没有测 FPS/帧时间、确定卡顿发生的时间点、Boss 战负载或暂停工具前后差异。不能把采样完成写成卡顿已解决、所有战斗图像已验收或暂停工具已实机通过。
4. 若继续比较暂停工具，单独记录启用前后的同一场景，先留 Codex 可采样；暂停 Codex 及其子进程可能把当前采样任务一并暂停。需要采集“Codex 也暂停”的阶段时，应先把采样器放到独立于 Codex 的进程中。
